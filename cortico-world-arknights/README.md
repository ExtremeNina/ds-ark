# cortico-world-arknights

Coopanion（Cortico 框架）的 World 扩展：把国服《明日方舟》PC 客户端接进桌宠。

当前交付的是「最小战斗闭环」的零件：

| 工具 | 做什么 | 不做什么 |
|---|---|---|
| `ark_connect` | 枚举本机窗口，按窗口名关键字找到客户端并建立连接，回报窗口名、类名、截图分辨率 | 不启动游戏、不切换账号 |
| `ark_screencap` | 抓取当前一帧，作为 PNG 附件随回执交给模型 | 不做识别 |
| `ark_set_paused` | 向配置的暂停按钮位置发一次点击（`true` 暂停 / `false` 继续），默认再补拍一帧作为附件 | 不确认游戏是否真的暂停，只提供点击后的画面供模型自己判断 |
| `ark_battle_state` | 抓一帧，用包内 PP-OCRv6 模型读出费用、生命值、剩余敌人、暂停横幅、手牌费用，并判断本局是否已结算（胜利/失败），附上同一帧 | 只读，不发任何点击；读不到的项如实列为「没读到」，不当成 0 |
| `ark_deploy` | 按模型给的 0~1 归一化坐标把手牌拖到地块、再拖出朝向，默认补拍一帧 | 只说「拖拽已发出」，不确认落位成功；不做网格坐标换算 |
| `ark_wait` | 等待指定毫秒（最多 10 秒），用于等费用回复 | 不截图、不点击、不确认任何游戏状态 |

扩展本身不做自动战斗，但提供了让模型自己打完一局的工具与剧本（见 `BATTLE_PLAYBOOK.md`）；不做选关、不做 Copilot 作业回退、不实现「代理指挥」。OCR 只在本地跑，模型随包提供；不发任何网络请求。

## 安装到 Coopanion（本机目录）

1. 在本目录执行：

   ```bash
   corepack pnpm install
   pnpm test
   ```

2. 打开 Coopanion 的**扩展页** → **从本机目录安装**（以 `link` 方式装入，不是拷贝）。
   选中的目录就是这个包目录（含 `package.json` 的那一层）。
3. **重启 Coopanion 进程**，扩展才会被加载。
4. 到 **World 总览**启用「明日方舟」，否则五个工具不会挂载。
5. 之后改了源码，**重启进程**才生效。
6. 出问题时在 **World 总览**关掉它，或直接卸载扩展。

安装前 Coopanion 只读 `package.json` 做声明校验，不会执行包里的代码；但扩展一旦启用就跑在 Coopanion 核心进程里，没有沙箱——请先自己读完源码再决定启用。

## 第一次使用要校准暂停按钮

暂停按钮的位置按**画面比例**存，**在同一宽高比下**换分辨率不用重新校准：

```json
{
  "worlds": {
    "arknights": {
      "enabled": true,
      "windowMatch": "明日方舟,Arknights",
      "screencapMethod": "Default",
      "inputMethod": "AnchoredTouch",
      "pauseButton": { "x": 0.966, "y": 0.071 },
      "verifyAfterClick": true,
      "resourceDir": ""
    }
  }
}
```

`x` / `y` 是 0~1 的比例（0 = 最左/最上，1 = 最右/最下），按 `像素 / (边长 - 1)` 归一化，也可以在扩展的 World 页表单里改，改完下一次工具调用立即生效。默认值 `0.966 / 0.071` 是真机实测的暂停键中心（1280×720 帧里的 1236,51）。

### 只有 16:9 是保证的

默认值是在 16:9 画面上标定的（1280×720、1920×1080 等）。换成 16:10、21:9 或用户拖出来的任意比例时，按钮的**相对位置会变**，坐标不再保证命中。扩展会在每次连接的第一帧之后检查一次比例，不是 16:9 就往日志里写一条提示（不进模型上下文，不会打扰对话）。

换比例后要重新标定：

1. 让游戏窗口保持在要用的比例上，进一场战斗。
2. 在仓库根的 `test/` 包跑 `pnpm smoke`，看输出的帧尺寸，用看图工具量出暂停键中心的像素坐标。
3. 跑 `pnpm smoke --click --pause <x>,<y>`，脚本会回显该像素对应的归一化值，并打印当前画面的宽高比；点中后把这两个比例填回配置。
4. `x = 像素x / (帧宽 - 1)`、`y = 像素y / (帧高 - 1)`，保留 3 位小数即可（上面的归一化值就是这个算法）。
5. 每个常用比例各标一组；扩展本身不做黑边检测与自动补偿，非 16:9 只提示不动手。

**怎么快速校准**：先进一场已经打过的关卡让战斗跑起来，把暂停键中心的位置按上面的算法填进去，然后在仓库根的 `test/` 包里跑 `pnpm smoke --click`，看游戏是否真的暂停。

## OCR：读战场数字

`ark_battle_state` 会把费用、生命值、剩余敌人、暂停横幅和手牌费用读出来。识别用的是 **MaaFramework 自带的 OCR**，模型随扩展发布（PP-OCRv6 small，占包体约 20 MB）——不需要安装 MAA、不需要配置、不联网：

1. 安装后即可用。第一次调用 `ark_battle_state` 时会加载模型（约 1~2 秒），之后复用；每次识别跑两遍（整帧 + 底部手牌条灰度），CPU 上合计约 0.5~0.8 秒，加上抓帧一秒左右。
2. 想换模型时把 `resourceDir` 指到一个目录：该目录下平铺 `det.onnx` / `rec.onnx` / `keys.txt`，或者填带 `model/ocr` 的资源包根。自定义目录优先，缺件时自动回落到包内模型。
3. 模型不可用时 `ark_battle_state` **不报失败**：仍然返回那一帧，回执里列出试过的路径与各自缺的文件，模型改看图。

包内模型位于 `assets/resource/model/ocr/`，三个文件必须平铺在这一层——MaaFramework 只按这三个固定文件名查找、不会进入子目录，放错层会在识别阶段表现为 0 行。

### 换更大的 OCR 模型（可选）

小字漏检偏多时（典型表现：手牌 12 张只读出六七张），可以换成 `ppocr_v6-medium`：从 MaaCommonAssets 的 `OCR/ppocr_v6/ppocr_v6-medium.zip` 解压出 `det.onnx` / `rec.onnx` / `keys.txt`，二选一：

1. 覆盖 `assets/resource/model/ocr/` 里的同名文件（自用方便，包体会变大）；
2. 放到任意目录，把 `worlds.arknights.resourceDir` 指过去（推荐，不动包内容）。

文件名与层级要求与 small 完全相同；换完跑 `pnpm smoke --state`，对比手牌条目数即可。

扩展只调用 `Resource.post_ocr_model()` 与 `Tasker.post_recognition()`，不加载 pipeline、不接管截图与点击。识别结果按**画面区域**归类（顶部条 / 中央横幅 / 右下费用 / 底部手牌），区间常量在 `src/battle/regions.ts`，注释里写了它们来自 1280×720 真机帧的位置。

读出来的东西有几条硬规则：

- 读不到就是 `null`，回执里列成「没读到：…」，绝不用 0 顶替。
- 暂停态是三态：认到横幅 / 没认到横幅（**不代表没暂停**）。
- 数字来自本机 OCR，可能出错，回执末尾固定带一句「请以附件画面为准」。
- 手牌只给费用与横坐标，读不出干员名字与职业——那些交给模型看图。
- 手牌会识别两次：整帧一次、底部手牌条**转灰度**再一次，按横向位置归并去重。去色能让压在浅色立绘上的卡费被检出（实测最后一张 24 费只有灰度那一路读得到），代价是每次多约 0.3 秒。
- 手牌费用容忍卡面图标被认成字母的前缀（`N16` → 16）；三位数是邻卡粘连（`118` = 邻卡的 1 + 18），按「去首位 / 去末位 + 费用上限 40」拆回两位（`118`→18、`167`→16），拆不出合法值就丢弃。中间那张卡被左右邻居把框挤没的情况救不回来，属于检测召回问题。

### 校准识别区间

进了战斗后跑 `pnpm smoke --state`：它会打印每一行识别结果的文字、归一化坐标、像素坐标与命中的区域名。当前标定以 1280×720 真机帧为准：卡费中心在 `y≈0.85`（`hand.y` 取 `[0.83, 0.875]`）、部署费用在 `y≈0.72`、`剩余可放置角色` 在 `y≈0.78`（`cost.y` 上限 0.82），两条带之间留 0.01 空档。某项一直「没读到」，就按打印出来的像素坐标去调 `src/battle/regions.ts` 里对应的区间，然后 `pnpm smoke --state` 再验一次。

### 分辨率、窗口比例与全屏

- **抓的是窗口客户区**（不含标题栏、任务栏），MaaFramework 再把短边压到 720：1920×1080 → 1280×720、3840×2160 → 1280×720、2558×1494 → 1233×720。
- 区域和点击都是相对**帧**的 0~1 比例，所以**分辨率本身不影响**识别与点击；影响的是**窗口比例**。
- **4K 全屏（16:9）不需要任何配置**：帧正好是 1280×720，与标定帧一致。建议用无边框全屏，独占全屏可能抓不到画面（黑图/桌面）。
- 屏幕是 16:10 时，如果游戏给 16:9 内容加了上下黑边，帧里内容区会被纵向压缩，卡费可能掉出 `hand` 带、暂停按钮会落到黑边上——这种情况要么把窗口改成 16:9，要么按冒烟输出的坐标重标。
- 暂停按钮在非 16:9 画面上按「距右边缘的余量」换算（16:9 下与旧值完全一致），所以窗口比例轻微不同也不会点空。偏差 ≤0.08 时日志只有一条 `[info]`（说明 x 已按余量换算、只有画面上下出现黑边才需要重标），偏差更大才 `[warn]`。
- 顶部条的 x 上界（0.72）是刻意收的：右上角的 `1X` 与暂停图标会被识别成 `I1`，数字纠错后会变成 `11`，圈进来就会冒充生命值。
- **改过窗口大小后先抓一帧**（或重新 `ark_connect`）再点击：暂停与部署都用最近一帧的尺寸换算，旧尺寸会点偏。

如果 `[ocr]` 是 **0 行**，先别动 ROI：`[info] OCR 模型加载自 …` 应指向 `…\assets\resource\model\ocr`。回执里出现「缺 det.onnx / rec.onnx / keys.txt」说明模型文件没随包发布或被移动；日志里出现 `Failed to load det or rec`（`det=0000000000000000`）说明模型根本没注册上，与区间无关，多半是模型与当前 `maa-node` 版本不兼容——用 `resourceDir` 指向 MaaCommonAssets 的 `ppocr_v4` 模型覆盖后重试。

## 部署干员：点选式

`ark_deploy` 收三个参数，都是模型从附件画面里量出来的：

```json
{ "card": { "x": 0.045, "y": 0.94 }, "tile": { "x": 0.42, "y": 0.55 }, "direction": "right" }
```

- `card` / `tile` 是 0~1 的归一化坐标（`x / (帧宽-1)`、`y / (帧高-1)`），`direction` 是 `up` / `down` / `left` / `right`。
- 工具先做「手牌 → 地块」拖拽（260ms），再在**地块上**往朝向方向拖 79 像素左右（画面高度的 11%），两次都是 `post_swipe`。
- 参数不合法（坐标越界、朝向不认识、地块贴边导致方向拖不出来）时**一次手势都不发**，直接返回可读原因。
- 回执只说「已从 A 拖到 B，再拖到 C 定朝向」，默认补拍一帧；不会说「已部署」。
- 想稳一点就先 `ark_set_paused(true)`，部署完再 `false`——暂停状态下的拖拽不会因为漏怪而失败。

## 让模型自己打完一局

扩展本身不做自动战斗，但把「模型自己打」缺的两样能力补齐了：**结算判定**与**等待**。

- `ark_battle_state` 的回执会说明「本局已结束（行动结束／胜利）」或「本局失败（作战失败）」，模型据此停下；已经结算时不再列「没读到」，避免拿费用/手牌误导决策。
- `ark_wait { ms }` 只睡不动作（最多 10 秒），用来等费用回复，比反复截图省 token。

循环与决策规则写在 [`BATTLE_PLAYBOOK.md`](./BATTLE_PLAYBOOK.md)：读状态 → 看结算 → 选牌下干员 → 等费用 → 再看状态。模型在 Coopanion 里按它执行即可——扩展不联网，也不需要任何 API key。

## 真机冒烟（不经过 Coopanion）

冒烟脚本不在本包内，放在仓库根的 `test/` 包里（它需要真机、游戏窗口与原生模块，不该随扩展发布）：

```bash
cd ../test
corepack pnpm install
pnpm smoke                                   # 只截图，存 <前缀>-before.png
pnpm smoke --state                           # 抓帧 + 识别战场数字，打印原始行与结构化结果
pnpm smoke --watch                           # 只读循环：每 3 秒读一次，认到结算自动退出
pnpm smoke --ocr                             # 只跑识别，额外打印原始明细（排障用）
pnpm smoke --click                           # 点配置里的暂停坐标，再存一张 <前缀>-after.png
pnpm smoke --click 60,555                    # 按像素点一个大目标，用来判断输入有没有送达
pnpm smoke --click --input SendMessage       # 换输入方式（默认 AnchoredTouch）
pnpm smoke --click --pause 0.966,0.071       # 现场校准暂停坐标，不用改源码
pnpm smoke --deploy 0.045,0.94,0.42,0.55,right  # 按归一化坐标部署：手牌x,y、地块x,y、朝向
pnpm smoke --resource D:\MAA\resource        # 临时指定 OCR 资源目录（不改配置）
pnpm smoke --window "明日方舟" --shot trial  # 换窗口关键字与输出前缀
pnpm smoke --screencap DXGI_DesktopDup       # 换截图方式
```

脚本会打印「控制器报告的尺寸」「本帧实际像素尺寸」「点击换算用的尺寸」「最终落点」，点击时还会回显该像素的**归一化值**（保留 3 位小数）与**当前画面宽高比**，方便按分辨率逐个补坐标。点击后自动补拍对照帧 `<前缀>-after.png`。

`--state` 会额外打印每行识别结果的「文字 / 归一化坐标 / 像素坐标 / 区域」，以及结构化后的 `{cost,life,enemies,paused,handCosts,result}`；`--deploy` 会打印两次拖拽的端点与时长，并把对照帧存成 `<前缀>-deploy-after.png`。

控制器尺寸与帧尺寸不一致是常态：MaaFramework 会把截图短边缩到 720（窗口 1920×1080 → 帧 1280×720），脚本会把它当 info 打印。只有当控制器尺寸明显大于窗口、且帧里能看到桌面背景时，才是整屏抓取。

脚本直接引用本包源码，改完扩展不用重装依赖；它会写出 `<前缀>-before.png`（操作前）与 `<前缀>-after.png` / `<前缀>-deploy-after.png`（操作后），可以拿它们核对截图是否正常、点击与拖拽有没有生效。这一步验证的是最不确定的四件事：窗口能不能被枚举到、后台截图是否出画面、所选输入方式能不能被游戏接受、OCR 模型能不能加载并读对位置。

## 配置项

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | `false` | 由 World 总览或部署配置打开 |
| `windowMatch` | `明日方舟,Arknights` | 窗口标题包含其一即命中，逗号分隔 |
| `screencapMethod` | `Default` | 取值见 `@maaxyz/maa-node` 的 `Win32ScreencapMethod`；`Default` 用后台可采的 `Background`（FramePool \| PrintWindow） |
| `inputMethod` | `AnchoredTouch` | 取值见 `Win32InputMethod`；实测能命中右上角小按钮且不抢前台，`SendMessage` 系在本客户端点不中 |
| `pauseButton` | `0.966 / 0.071` | 暂停按钮中心的比例坐标，只在 16:9 下保证 |
| `verifyAfterClick` | `true` | 暂停/恢复点击后补拍一帧作为附件；关掉可省一次抓帧与一张图的 token |
| `resourceDir` | 空 | 可选覆盖：目录下平铺 `det.onnx` / `rec.onnx` / `keys.txt`，或填带 `model/ocr` 的资源包根。留空即用包内 PP-OCRv6 small 模型 |

## 接进 Coopanion：完整流程与验收

真机冒烟全绿之后再接线（冒烟只验证底层，不经过 Coopanion）：

1. 本目录 `corepack pnpm install && pnpm test`，确认全部用例通过。
2. 扩展页 → 从本机目录安装（`link`）→ **重启 Coopanion 进程**。
3. World 总览启用「明日方舟」；`resourceDir` 留空即可（想换模型再填），保存。
4. 进一场 1-7（或任意已解锁的关卡），让战斗跑起来，然后逐条验收：

| 步骤 | 让大肥鱼做什么 | 判定标准 |
|---|---|---|
| 1 | `ark_connect` | 回执给出窗口名与 `1280×720` 之类的分辨率，没有「拿不到画面尺寸」 |
| 2 | `ark_battle_state` | 回执里有费用/生命/敌人数字，附一张图；日志里有一条「OCR 模型加载自 …」 |
| 3 | 对比第 2 步的数字与画面 | 费用与左下角数字一致、生命与顶部一致；不一致就回去校准 `regions.ts` |
| 4 | `ark_set_paused(true)` | 回执附图中出现 PAUSE 浮层 |
| 5 | `ark_deploy`（从第 2 步的图里挑手牌与地块） | 回执附图中目标地块上出现干员，朝向箭头正确 |
| 6 | `ark_set_paused(false)` | 回执附图中浮层消失，干员开始攻击 |

另外单独验两条降级，确认「不知道」不会被说成「没问题」：

- 把 `assets/resource/model/ocr/keys.txt` 临时改个名再调用 → `ark_battle_state` 仍然返回一张图，并说明「没找到可用的 OCR 模型…缺 keys.txt」；它不算失败，模型应当改看图而不是报错停住。验完记得改名回来。
- 战斗中故意让某项落在识别区间之外（比如换了个 UI 布局）→ 回执里出现「没读到：…」，而不是 0。

判定要点：第 4~6 步允许失败一次（拖拽被忽略是已知可能），但**每次失败都要能从附件画面看出「没落位」**——如果回执说拖了、图里却什么都没有，说明手势没送达，先把 `inputMethod` 换成 `AnchoredTouch` 再试，仍失败则停下来查权限与输入方式，不要连发。

验收记录建议贴回仓库的 issue 或对话里：哪一步、什么图、什么输入方式。真机操作由使用者本人执行。

## 权限要求（实测踩过）

**Coopanion 与游戏必须是同一权限级别。** 如果游戏以管理员身份运行、而 Coopanion 不是，Windows 的 UIPI 会同时拦掉两件事：

- 后台截图失败，连接直接被拒（状态码 `4000`），MaaFramework 日志里会出现
  `SetWindowLongPtr failed ... GetLastError()=5`
- 合成点击（`SendMessage` / `PostMessage`）被丢弃，工具回执照样说「已发送点击」，但游戏毫无反应

两种解法：把游戏改成普通权限启动（启动器/游戏 exe 属性 → 兼容性 → 取消「以管理员身份运行」），或者让 Coopanion 也以管理员身份运行。前者更安全。

诊断时可以只截一个普通窗口（比如记事本）做对照：同样的 `Background` 方式能连上普通窗口却连不上游戏，就是权限不对等。

## 已知风险

- **点击可能不生效**：默认的 `AnchoredTouch` 实测能点中暂停键与倍速键，也不把游戏抢到前台，但仍然可能被游戏某次更新忽略。`SendMessage` / `PostMessage` 系更静默，但实测在本客户端点不中右上角的小按钮；`Seize` 能点但会抢占鼠标。注意：MVP 文档里「后台静默执行」这条验收指标在部分游戏上可能根本达不到。
- **暂停坐标只在 16:9 下保证**：默认值按 16:9 标定，换宽高比后不保证命中。扩展只在第一帧之后往日志里提示一次「不是 16:9」，不做黑边检测与坐标补偿；重标步骤见上一节。
- **补拍有代价**：`verifyAfterClick` 默认开启，每次暂停/恢复都会多抓一帧，并把这张图放进模型上下文（多一次截图延迟、一张图的 token）。不想要就把它关掉，回执退回纯文字。
- **截图可能全黑**：独占全屏、HDR、多显卡切换、窗口最小化都会影响。`Background` 系对最小化窗口有伪最小化支持，其他方式会失败。
- **`DXGI_DesktopDup` 抓到的是整屏**：实测它会把整个桌面按比例缩放后交回来（例如 2560×1600 的桌面变成 1152×720 的帧），游戏窗口只是其中一块。用这种方式算出来的点击坐标落在整屏坐标系里，点不中游戏按钮。排查时可以用它验证「能不能看到画面」，但**不要用它做点击验证**。扩展内部已改成始终按「最近一帧的真实像素尺寸」换算，并在帧尺寸与控制器尺寸不一致时记一条 warn。
- **识别会读错**：OCR 数字来自本机模型，字号小、背景亮、遮罩多时都可能读成别的数。回执固定带「请以附件画面为准」，模型不该拿它当精确值向用户断言。读不到时是「没读到」而不是 0；暂停态没认到横幅也不等于没暂停。
- **部署只是「手势已发出」**：`ark_deploy` 保证两次 `post_swipe` 被控制器接受，不保证游戏真的落位、朝向正确。落位与否只能从补拍的附件里看；失败一次可以重试一次，但不要连发（每次拖拽都会真的动游戏）。
- **只有最小闭环**：自动通关、选关导航、倍速控制、失败计数与 Copilot 作业回退**都没有做**，代理指挥也没有自动化。结算判定只做到「认到结算横幅」这一层：认到就告诉模型可以停，认不到不代表一定还在打。
- **游戏条款**：自动化操作可能违反游戏服务条款，风险由使用者承担。请只在自己的账号上、以不破坏公平性的方式使用。
- **只支持 Windows**：`package.json` 里 `os` 为 `win32`，其他平台会被拒绝安装。

## 隐私

- 不读取、不保存、不上传 API Key 或任何凭据；扩展不读 `ctx.secret()`。
- 不发网络请求，不下载任何资源。OCR 模型随包发布，从 `assets/resource/model/ocr` 读取；`resourceDir` 只是可选覆盖，同样只在本机内存里加载。
- 截图（含 `ark_set_paused` 与 `ark_deploy` 的补拍）只在本机内存里流转一次：作为工具回执的附件交给 Coopanion，由 Coopanion 决定是否发给**你自己配置的模型端点**。也就是说，**画面会进入模型上下文**——如果不希望画面离开本机，请不要接云端模型，或不要调用 `ark_screencap` / `ark_battle_state` 并把 `verifyAfterClick` 关掉。
- OCR 结果（费用、生命、敌人、手牌费用）会写进回执文本，随同一次请求进入模型上下文；它不是截图，但同样是画面信息的摘要。
- 日志只记录连接成功与错误原因，不记录截图内容、窗口句柄、用户目录。
